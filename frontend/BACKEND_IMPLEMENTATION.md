# Backend Implementation Plan — SHADAB RestaurantOS (Node.js)

> This document is a blueprint for implementing a **Node.js** backend for the existing React frontend. The frontend currently keeps all state in-memory via `frontend/src/lib/app-state.tsx` and `frontend/src/data/seed.ts`; this plan replaces that with a persisted PostgreSQL-backed REST + WebSocket API.

---

## 1. Context and goals

The existing application is a TanStack Start React prototype. All data (tables, orders, reservations, bills, staff, menu, stock) is stored in browser state and is lost on refresh. The workflows are described in `frontend/workflow.md`; the data contracts are defined in `frontend/src/data/seed.ts`.

This plan assumes:

- **Backend runtime:** Node.js (v20+ LTS).
- **API style:** REST over HTTP for CRUD + WebSocket/Socket.IO for real-time updates.
- **Database:** PostgreSQL (self-hosted, Neon, Supabase, or AWS RDS).
- **ORM:** Drizzle ORM.
- **Frontend remains React/TanStack Router.** It will call the API with `fetch` or TanStack Query.
- **Auth:** JWT or session cookies with role-based access.
- **Real-time:** Socket.IO rooms per `outletId` (kitchens, cashiers, waiters subscribe to their own rooms).

### Goals

1. Persist every mutable entity from `frontend/src/data/seed.ts` and `frontend/workflow.md`.
2. Enforce the table, order, kitchen, billing, and reservation state machines.
3. Support multi-tenancy (organizations, outlets, sections/floors).
4. Enable real-time collaboration across multiple POS/kitchen screens.
5. Migrate the frontend route-by-route to API calls.

---

## 2. Recommended Node.js stack

| Layer | Choice | Rationale |
|---|---|---|
| HTTP framework | **Fastify** (or **Express**) | Fastify is faster and has excellent validation hooks. Use Express if the team is more familiar with it. |
| Real-time | **Socket.IO** | Battle-tested, room-based pub/sub, works behind most reverse proxies. |
| Database | **PostgreSQL** | ACID, supports row-level locking for bill numbers, well-supported by Drizzle. |
| ORM | **Drizzle ORM** + `drizzle-kit` | Type-safe, SQL-like syntax, migrations. |
| Validation | **Zod** | Already in `package.json`; validates request bodies and query params. |
| Auth | **Better Auth** or a hand-rolled JWT/session cookie | Better Auth is framework-agnostic and works with Node; hand-rolled is acceptable for a controlled rollout. |
| Password hashing | **bcrypt** or **Argon2** | Standard. |
| Environment config | **dotenv** or `process.env` loaded via a config module | Keep secrets out of the repo. |
| Logging | **pino** (Fastify default) or **winston** | Request + business event logging. |
| Testing | **Vitest** (already used in the frontend build) | Unit tests for services, integration tests for routes. |

### Repository layout

Two recommended shapes:

- **A. Same repo, `backend/` and `frontend/` folders:** `backend/` (currently an empty directory at the repo root) contains the Node API; `frontend/` contains the existing React frontend. Each folder has its own `package.json`, or a root `package.json` with separate scripts.
- **B. Separate repo:** `restaurantos-backend` for the Node API, `restaurantos-frontend` for the current project.

This plan uses **same-repo `backend/` at the repository root.**

### Important frontend changes

- `frontend/src/lib/app-state.tsx` becomes a thin layer or is removed. Routes use `useQuery`/`useMutation` calling the API.
- `frontend/src/data/seed.ts` is moved to the backend as seed/migration data for the default `SHADAB` outlet.
- Components that currently call `setTables` / `setOrders` will call HTTP endpoints instead.
- The kitchen display uses Socket.IO to receive ticket updates instead of local fixtures.

## 6. Business logic reference

This section calls out the most important backend rules. The exact code lives in service modules (e.g. `backend/src/services/billing.ts`).

### 6.1 Tax and discount math

Re-implement the cashier logic from `frontend/src/routes/billing.tsx` on the server. Example in paise:

```ts
function computeBillTotals(
  lines: BillLine[],
  discount: { kind: "flat" | "percent"; value: number },
  serviceChargeRate: number,
  taxRates: { cgst: number; sgst: number }
) {
  const active = lines.filter((l) => l.kitchen_status !== "cancelled");
  const standard = active.filter((l) => !l.mrp);
  const mrpItems = active.filter((l) => l.mrp);
  const standardSubtotal = standard.reduce((s, l) => s + l.qty * l.unitPrice, 0);
  const mrpSubtotal = mrpItems.reduce((s, l) => s + l.qty * l.unitPrice, 0);
  const discountAmount =
    discount.kind === "flat"
      ? Math.min(discount.value, standardSubtotal)
      : Math.round((standardSubtotal * discount.value) / 100);
  const taxable = standardSubtotal - discountAmount;
  const totalTaxRate = taxRates.cgst + taxRates.sgst;
  const tax = Math.round((taxable * totalTaxRate) / 100);
  const serviceCharge = Math.round((taxable * serviceChargeRate) / 100);
  const preRound = taxable + tax + serviceCharge + mrpSubtotal;
  const total = Math.round(preRound);
  return {
    subtotal: standardSubtotal + mrpSubtotal,
    discount: discountAmount,
    tax,
    serviceCharge,
    total,
    rounding: total - preRound,
  };
}
```

### 6.2 Multi-kitchen routing

On `POST /api/v1/orders/:id/send-to-kitchen`:

1. Increment the KOT batch number for this order.
2. For each cart line, look up `menu_items.kitchen_id`. If none, assign a default kitchen.
3. Insert `order_items` with `kitchen_status = 'placed'` and `table_status = 'pending'`.
4. Emit `kitchen.ticket` to each relevant `kitchen:{kitchenId}` room.
5. Update the parent `orders.status` to `open` (or `partially-served` if some items are already served).

The kitchen display receives all items in a batch, but greys out any `order_item` whose `kitchen_id` does not match the logged-in user's kitchen.

### 6.3 Table groupings

- **Merge:** Reject if any selected table has an order in `open`, `partially-served`, or `fully-served`.
- **Split:** Reject if the sum of sub-table capacities exceeds the parent. Move the existing order to the first sub-table (`Table 1a`).
- **Unsplit:** Allow only when all sub-tables are `available` and have no active orders.
- **Transfer:** Allow only when the source table has no active order.

### 6.4 Takeaway lifecycle

- `order_type = 'takeaway'`, `table_id = NULL`.
- Customer name/phone stored on `orders`.
- Kitchen display uses the same ticket format but exposes `takeaway-all-ready` only when every item is `cooking` or `ready`.

### 6.5 Stock-out

`POST /api/v1/menu-items/:id/stock-out` toggles `stock_outs.active`. The menu list endpoint excludes items with an active stock-out for the outlet. Existing order items are not affected.

### 6.6 Notifications

Persist to `notifications` and emit to the appropriate Socket.IO room:

| Event | Room | Payload |
|---|---|---|
| Item ready | `waiter:{table.waiter_id}` | `{ type: 'item.ready', tableId, item }` |
| Takeaway all ready | `outlet:{outletId}:counter` | `{ type: 'takeaway.ready', orderId }` |
| Bill requested | `outlet:{outletId}:billing:{sectionId}` | `{ type: 'bill.requested', tableId }` |
| Stock out | `outlet:{outletId}:menu` | `{ type: 'stock.updated', menuItemId }` |

## 7. Real-time / Socket.IO design

### Room strategy

```
outlet:{outletId}
outlet:{outletId}:tables
outlet:{outletId}:kitchen:{kitchenId}
outlet:{outletId}:billing:{sectionId}
waiter:{staffId}
counter:{outletId}
```

### Client join logic

```ts
// backend/src/socket/index.ts
io.on("connection", (socket) => {
  const { outletId, staffId, role, kitchenId } = socket.user;

  socket.join(`outlet:${outletId}`);
  socket.join(`outlet:${outletId}:tables`);
  if (kitchenId) socket.join(`outlet:${outletId}:kitchen:${kitchenId}`);
  if (role === "cashier") socket.join(`outlet:${outletId}:billing:${sectionId}`);
  if (role === "waiter") socket.join(`waiter:${staffId}`);
  if (role === "captain") socket.join(`counter:${outletId}`);
});
```

### Broadcasting from services

```ts
// backend/src/services/events.ts
import { io } from "@/socket";

export function emitTableUpdate(outletId: string, table: Table) {
  io.to(`outlet:${outletId}:tables`).emit("tables.updated", table);
}
```

## 8. Auth and authorization

1. **Session** — HTTP-only cookie `sessionId` or stateless JWT.
2. **Middleware** — Fastify `preHandler` that:
   - Validates the token/session.
   - Loads `user`, `staff`, and `roles` for the request.
   - Rejects if `outletId` is not in the user's allowed outlets.
3. **Permission table**:

| Action | Allowed roles |
|---|---|
| Onboarding | `admin`, `outlet-manager` |

## 11. Example implementation

### Fastify route: seat table

`backend/src/routes/tables.ts`:

```ts
import { FastifyInstance } from "fastify";
import { z } from "zod";
import { seatTable } from "@/services/tables";
import { requireAuth, requireRole } from "@/middleware/auth";

const SeatTableBody = z.object({
  tableId: z.string().uuid(),
  guests: z.number().int().min(1),
  waiterId: z.string().uuid().optional(),
});

export default async function tableRoutes(app: FastifyInstance) {
  app.addHook("preHandler", requireAuth);

  app.post<{ Body: z.infer<typeof SeatTableBody> }>(
    "/:outletId/tables/:tableId/seat",
    {
      preHandler: [requireRole(["captain", "admin"])],
      schema: { body: SeatTableBody },
    },
    async (request, reply) => {
      const { outletId, tableId } = request.params as { outletId: string; tableId: string };
      const { guests, waiterId } = request.body;
      const table = await seatTable({ outletId, tableId, guests, waiterId, db: request.db });
      request.io.to(`outlet:${outletId}:tables`).emit("tables.updated", table);
      return table;
    }
  );
}
```

### Drizzle schema snippet

`backend/src/db/schema.ts`:

```ts
import { pgTable, uuid, text, integer, boolean, timestamp } from "drizzle-orm/pg-core";

export const tables = pgTable("tables", {
  id: uuid("id").primaryKey().defaultRandom(),
  outletId: uuid("outlet_id").notNull(),
  sectionId: uuid("section_id").notNull(),
  number: integer("number").notNull(),
  name: text("name").notNull(),
  capacity: integer("capacity").notNull().default(4),
  status: text("status").notNull().default("available"),
  guests: integer("guests").notNull().default(0),
  waiterId: uuid("waiter_id"),
  startedAt: timestamp("started_at", { withTimezone: true }),

});
```

## 12. Risks and open decisions

1. **Frontend deployment mode** — The frontend can stay as a static SPA (Vite build to `dist/`) or use TanStack Start SSR. With a Node backend, the easiest path is a static SPA or a TanStack Start app that calls the Node API for data.
2. **Bill number concurrency** — Use `SELECT ... FOR UPDATE` on `bill_number_counters` to avoid duplicate bill numbers under load.
3. **Cashier hard-coding** — `frontend/src/routes/billing.tsx` hard-codes `cashier: "Shabbir"`. The backend should use the authenticated `staff_id`.
4. **Kitchen state mismatch** — The frontend `OrderLine.status` enum (`pending`, `sent-to-kitchen`, `on-table`, `cancelled`) does not match the intended `placed → accepted → cooking → ready → served` flow. Add a mapping in the API response.
5. **Socket.IO scaling** — For a single Node server, in-memory Socket.IO is fine. For horizontal scaling, add Redis adapter (`socket.io-redis-adapter`).
6. **Menu seed vs. admin UI** — Seed data is a quick start; admin UI for menu management should follow in a later phase.
